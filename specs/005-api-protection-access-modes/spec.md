**已批准的產品語意**：capability signing key 的 verify-only 只禁止簽發新 capability，不禁止輪替前已簽發且仍有效 capability 的首次執行。本人 Session、當下資格、限流、成本、epoch authority 及原子首次 grant 檢查全部成立，且原操作從未取得 grant 時，正常輪替後仍可首次執行一次。request fingerprint 的 verify-only 只用於既有操作比較，不能將重送當新操作；已有 grant 永不再取得第二次 grant。洩漏撤銷或 epoch 退役拒絕新 grant，但不追溯作廢原入帳、uncertain 占用及保守結算。此語意及E01～E10具體推薦已批准用於本機實作與隔離測試；production及真實操作仍受上方gate限制。

**已批准語意的驗收情境（本機已執行；T157～T161，正式仍未驗）**：正常signing輪替後未grant且有效的舊capability，在全部gate成立時首次grant恰一次；相同操作重送409 duplicate、不同內容409 conflict且第二grant為0；fingerprint按既有記載version比較，不用新key重算。撤銷／退役先於reserve則新grant為0；grant先成立則原used／reserved／uncertain不回退，晚到只沿原accounting authority處理。免費簽發確認不簽新capability、不延長expiry、不grant。資格失效403優先，不洩漏操作資訊。

## 已確認產品政策

**2026-10-06 本機契約格式同步**：管理追加與 engine 的週鍵統一使用 `YYYY-Www`（ISO 週年／週次）；原管理範例的 `-AsiaTaipei` 只屬格式差異，已移除。Asia/Taipei 週一 00:00 重置、僅核准當週有效、日額度不受追加影響的既有政策不變。

1. Public 免登入，僅能使用完全不呼叫六個付費 API 的功能。
2. 使用者可註冊與登入；完成註冊或登入本身不取得付費 API 權限。
3. 管理者明確核准後，使用者可獲第一級或第二級資格：第一級估算用量上限為 US$3／日、US$15／週；第二級為 US$10／日、US$50／週。
4. 達每週上限後，只有管理者明確追加核准才可再用付費 API；追加核准前仍可使用 Public 功能。
5. 額度由可信後端以估算、原子預留與結算控制；它不是供應商帳單精確保證，前端與使用者不得自行提高。
6. 每日上限獨立有效。即使週額度獲追加核准，除非另行批准，仍不得越過當日上限。
7. 每次六個付費 API 呼叫前，後端必須以可信的最大估算成本同時原子預留日額度與週額度；若任一上限不足，必須在呼叫付費上游前拒絕。不得先呼叫供應商再更新計數。
8. 內部估算額度是存取邊界，不是供應商實際帳單保證；仍必須另以供應商帳戶可用的預算告警或用量限制作為獨立防線，不得宣稱 App 內計數能保證實際帳單絕不超額。
9. 管理者必須透過獨立管理者儀表板管理登入者的付費 API 核准資格、等級與週額度追加；管理資料與管理操作必須由後端逐請求驗證管理者權限，一般登入者、第一／第二級使用者與未登入者皆不得讀取管理資料或執行管理操作。管理者帳號的指定與撤銷必須來自可信、不可由使用者自行提升權限的來源，後端不得信任前端送出的 role 欄位。
10. **Geoapify 方案 A 已核准，圖磚代理為已同意架構方向**：Public、未登入、已登入但未核准／已撤銷／已到期，以及日或週額度使付費功能暫不可用者，地圖位置只顯示靜態東京風格示意圖；不得初始化會載入 Geoapify 圖磚的互動地圖元件，也不得以背景預取、自動重試或舊分頁觸發 Geoapify 圖磚或 `/api/places`。只有有效核准且日／週額度可用者得使用既有互動地圖；其圖磚請求必須全部經由後端圖磚代理逐請求驗證 Session、核准資格與圖磚額度後才轉發，前端不得保留可繞過代理的直連路徑或可任意指定上游位置的參數；Places 搜尋仍須由後端逐請求執行授權與額度控制。
11. **「額度暫不可用」的產品定義（2026-10-06 重審補充，技術數值見 plan.md §4.5）**：指日或週剩餘額度已低於「當下具有可信上界、有效期內、實際啟用且版本／成本參數摘要未封鎖的付費功能，在其合法輸入上限下、最少仍有一個可以預留」的最低門檻。G 依當下權威 registry／價表及上述狀態計算，不採建置期固定值或歷史 fixture。單一功能因「所需預留金額高於剩餘」而被拒（例如長文字語音合成），只影響該功能，須以與「額度已滿」不同的文案引導使用者縮短內容，**不得**因此將地圖、其他較低成本功能或公開功能視為不可用。

| 管理者（可信來源指定，非使用者自報） | 允許 | 依本身有效資格與日／週額度決定互動地圖或靜態示意圖 | 受本身額度約束；對他人執行追加無固定次數或倍數上限，但須逐次決定並可稽核（見 FR-040） | 允許，且逐請求驗證 | 允許，且逐請求驗證、原子執行、留稽核紀錄 |

### 已核准政策與仍需獨立批准事項

1. **週額度追加參數**：管理者對指定使用者、指定週逐次決定正值金額與次數，不設固定次數或累計倍數上限；有效期限不得跨週，日上限仍獨立有效。此政策已核准，不再列為待決上限。
2. **管理者作業方式**：獨立管理者儀表板與 M1 server-side allowlist 架構已核准；真實 OIDC 管理者 subject、環境變數設定、外部服務啟用及正式部署仍須獨立批准。
3. **靜態示意圖資產**：方案 A 已核准，但聊天中提供的圖僅為視覺參考，並非真實地理資料，且本機 repository 目前沒有可據此視為已存在的圖片檔。正式圖片的取得、授權、最佳化與整合仍受資產交付阻擋；本規格不新增或指定虛構資產路徑。

## User Scenarios & Testing

### User Story 1 - Public 使用公開功能 (Priority: P1)

Public 訪客不需登入，可瀏覽東京百科、旅遊日文、公開音檔、App Shell 與既有公開資料；所有會使六個付費 API 呼叫上游的操作都不會送出付費請求。

**Independent Test**: 未登入狀態逐一操作各六個付費功能入口，確認每次都在上游呼叫前被拒絕，並在隔離環境確認前端發出的地圖位置 Geoapify 圖磚代理請求與 `/api/places` 呼叫均為零（口徑見 FR-044）；公開內容仍可使用。

**Acceptance Scenarios**:

1. **Given** Public 訪客瀏覽公開內容，**When** 閱讀、搜尋公開資料或播放 bundled MP3，**Then** 不需登入且不呼叫六個付費 API。
2. **Given** Public 訪客操作會使用任一付費 API 的送出、錄音轉錄、附近搜尋、語音合成、OCR 或照片翻譯，**When** 請求抵達後端，**Then** 回應資格未核准的拒絕，且不呼叫上游付費服務。
3. **Given** Public 或未登入訪客進入探索附近，**When** 地圖位置呈現，**Then** 顯示明確標示「示意圖」的靜態東京風格圖片，不初始化互動地圖元件、不載入 Geoapify 圖磚，且不自動呼叫 `/api/places`。
4. **Given** Public 或未登入訪客重新整理、從舊分頁恢復、切換模式或資格狀態變更，**When** 畫面重新判定為受限狀態，**Then** 不得以背景預取、自動重試或既有前端狀態發出 Geoapify 圖磚或 `/api/places` 請求。

### User Story 2 - 註冊或登入但未核准者使用公開功能 (Priority: P1)

使用者可完成註冊與登入，但若沒有有效核准等級，行為與 Public 的付費限制一致，公開內容仍可使用。

**Independent Test**: 以已登入但無有效核准紀錄的帳號，直接呼叫六個端點；六者均被拒絕且 mock 上游未被呼叫。

**Acceptance Scenarios**:

1. **Given** 使用者已登入但從未獲核准、已被撤銷或核准已過期，**When** 呼叫任一付費 API，**Then** 回應 403，且不呼叫上游。
2. **Given** 使用者僅完成註冊或登入，**When** 系統判定付費 API 資格，**Then** 不得把登入視為核准。
3. **Given** 使用者提供自稱 email、user ID、等級或額度欄位，**When** 後端判定資格，**Then** 僅信任可信身分與後端核准紀錄。
4. **Given** 使用者未核准、資格被撤銷或核准已過期，**When** 進入或停留在探索附近，**Then** 地圖位置立即採靜態示意圖，且不得初始化圖磚元件或由舊分頁呼叫 `/api/places`。

### User Story 3 - 核准等級使用付費 API (Priority: P1)

管理者核准使用者為第一級或第二級後，使用者在日與週估算額度內可使用六個付費 API，且每一請求均由後端即時檢查。

**Independent Test**: 對各級測試帳號逐一呼叫六端點，在額度內確認成功；第一級與第二級分別使用指定上限。

**Acceptance Scenarios**:

1. **Given** 第一級核准有效，**When** 估算使用量未達上限，**Then** 可呼叫六端點，日／週上限為 US$3／US$15。
2. **Given** 第二級核准有效，**When** 估算使用量未達上限，**Then** 可呼叫六端點，日／週上限為 US$10／US$50。
3. **Given** 核准使用者送出任一付費請求，**When** 後端能界定該端點可信的最大估算成本，**Then** 必須先以該成本上界原子預留日與週額度，成功後才可呼叫上游。
4. **Given** 任一端點無法在呼叫前界定可信最大成本，**When** 使用者送出請求，**Then** 系統必須先限制輸入、輸出、時長或其他計費參數；仍無法界定時不得以本額度政策放行。
5. **Given** 多個請求同時抵達餘額邊界，**When** 後端預留額度，**Then** 總放行量不得超過核准上限，且不得共同花用同一筆剩餘額度。
6. **Given** 使用者重新整理頁面、重複提交或直接呼叫 API，**When** 付費請求抵達後端，**Then** 每次都重新執行相同後端預留與額度檢查，不得以舊前端畫面或自報額度繞過。
7. **Given** 核准使用者的日與週額度皆可用，**When** 進入探索附近，**Then** 既有互動地圖可呈現；只有使用者明確發起附近搜尋時才可呼叫 `/api/places`，且後端仍須先完成授權與額度控制。

### User Story 4 - 資格與等級變更即時生效 (Priority: P1)

管理者新增核准、撤銷資格、變更等級、拒絕或使核准到期後，下一次受保護請求反映最新狀態。

**Independent Test**: 在不登出的情況下撤銷、降級、使核准到期或變更等級後再次呼叫端點，驗證最新決策生效。

**Acceptance Scenarios**:

1. **Given** 核准被撤銷、拒絕或到期，**When** 使用者下一次呼叫付費 API，**Then** 回應 403，公開功能不受影響。
2. **Given** 使用者等級被變更，**When** 下一次付費請求到達，**Then** 後端採用新等級的日／週上限。
3. **Given** 已登入 Session 尚未過期，**When** 資格被撤銷，**Then** Session 不得讓下一次付費請求繞過撤銷。
4. **Given** 互動地圖已開啟而使用者資格被撤銷、拒絕或到期，**When** 最新資格生效，**Then** 地圖位置切換為靜態示意圖，停止後續圖磚載入，且舊元件、舊分頁或重試不得觸發 `/api/places`。

### User Story 5 - 日額度與週額度耗盡後的恢復 (Priority: P1)

使用者達日額度時暫停付費 API 到下一個日窗口；達週額度時，必須等待管理者明確追加核准，且每日上限仍獨立有效。

**Independent Test**: 對各級帳號分別耗盡日與週額度，確認不同狀態與恢復條件，並確認無上游呼叫。

**Acceptance Scenarios**:

1. **Given** 使用者達當日額度但未達週額度，**When** 再次請求，**Then** 回應 429「當日額度已滿」，直到下一個可信後端日窗口才可手動重試。
2. **Given** 使用者達每週額度，**When** 再次請求，**Then** 回應 429「每週額度已滿，等待管理者核准」，直到有效追加核准或新的週窗口才可手動重試。
3. **Given** 使用者取得週額度追加核准，**When** 當日額度也已滿，**Then** 仍回應當日額度已滿；追加不自動取消日額度。
4. **Given** 使用者被拒絕或尚未取得週額度追加核准，**When** 使用公開功能，**Then** 公開功能維持可用。
5. **Given** 使用者接近日或週額度邊界，**When** 單次請求的可信最大估算成本會使任一窗口超額，**Then** 後端必須拒絕該請求且不呼叫上游，即使前端顯示仍有部分剩餘金額。
6. **Given** Asia/Taipei 的日窗口跨過每日 00:00，或週窗口跨過週一 00:00，**When** 使用者再次手動請求，**Then** 可信後端以新的窗口與仍有效的核准／追加狀態重新計算，並提供下一次重置時間；瀏覽器時鐘偏移、跨時區操作與夏令時間變化均不得提前或延後恢復。
7. **Given** 核准使用者的日或週額度已滿，**When** 進入、重新整理或停留在探索附近，**Then** 地圖位置顯示靜態示意圖，前端發出的圖磚代理請求與 `/api/places` 請求均為零（口徑見 FR-044）；窗口重置或追加核准後仍須依最新後端狀態重新判定，不得自動重送舊搜尋。

### User Story 6 - 防護服務故障 fail-closed (Priority: P2)

必要的身分、核准、額度或原子計數依賴無法確認時，系統停止新的付費上游呼叫，但不停止公開功能。

**Acceptance Scenarios**:

1. **Given** 必要防護服務逾時或錯誤，**When** 請求付費 API，**Then** 回應 503，且不呼叫上游。
2. **Given** 故障恢復，**When** 使用者重新明確操作，**Then** 系統重新執行完整資格與額度檢查；不得自動重送舊請求。
3. **Given** 額度查詢失敗或資料已過期，**When** 前端需顯示額度資訊，**Then** 不得顯示虛假的剩餘金額；付費 API 必要計數服務故障時維持 fail-closed。

### User Story 7 - 查看自身額度狀態與請求結算 (Priority: P2)

有效核准使用者在付費功能入口可查看自身核准等級，以及可信後端回傳的日／週已使用、預留中、剩餘估算額度與重置時間；每位獲核准使用者各自計算額度，同級使用者不共用；每次付費請求完成後，顯示必須依後端最新狀態更新。

**Independent Test**: 以有效核准帳號執行成功、明確未計費失敗、逾時、不確定是否計費、重整頁面與額度查詢故障情境，確認畫面只呈現可信後端狀態且不暴露其他使用者或邀請名單。

**Acceptance Scenarios**:

1. **Given** 使用者開啟任一付費功能入口，**When** 額度查詢成功，**Then** 顯示核准等級、日／週已使用、預留中、剩餘估算額度與重置時間，且只顯示該使用者可見的範圍。
2. **Given** 一次付費請求成功完成，**When** 後端取得供應商用量或套用既定估算規則完成結算，**Then** 已使用、預留中與剩餘估算額度更新；不得把估算成本宣稱為供應商實際帳單。
3. **Given** 上游明確回報未計費失敗，**When** 請求結束，**Then** 後端依一致規則釋放或調整預留，並更新顯示。
4. **Given** 請求逾時或結果不確定是否已計費，**When** 後端結算，**Then** 採保守規則處理，不得以未知狀態立即恢復可用額度。
5. **Given** 額度查詢失敗、資料過期或分頁長時間未更新，**When** 使用者查看入口，**Then** 顯示無法確認狀態，而非虛假的剩餘金額；使用者仍可查看公開內容。
6. **Given** 多個分頁或直接 API 呼叫同時送出請求，**When** 額度不足，**Then** 後端以原子預留拒絕超額請求，前端顯示不得影響授權結果。
7. **Given** 使用者資格被撤銷、降級或追加核准到期，**When** 下一次付費請求或額度查詢發生，**Then** 顯示與後端決策反映最新狀態，公開功能仍可用。

### User Story 8 - 管理者透過獨立儀表板掌握核准與用量 (Priority: P1)

管理者需要獨立於一般使用者介面的儀表板，以掌握登入者、核准資格與六個付費 API 的使用狀況，並完成核准、拒絕、切換等級、撤銷與追加額度等操作；一般登入者、第一／第二級使用者與未登入者皆不得讀取管理資料或執行管理操作。

**Independent Test**: 以未登入或 Session 無效身分、一般登入者、第一級、第二級身分逐一嘗試讀取管理資料端點與呼叫管理異動端點，確認前者回應 401、後四者回應 403，兩者均無資料外洩；以可信來源指定的管理者身分執行相同操作，確認可正常讀取與異動，且異動具原子性與稽核紀錄。

**Acceptance Scenarios**:

1. **Given** 使用者未登入或 Session 無效，**When** 呼叫任一管理資料端點或管理異動端點，**Then** 回應 401，且不回傳任何管理資料。
2. **Given** 使用者已登入但未核准、已撤銷、已到期、第一級或第二級核准，**When** 呼叫任一管理資料端點或管理異動端點，**Then** 回應 403，且不回傳任何管理資料。
3. **Given** 使用者身分為可信來源指定的管理者，**When** 開啟管理者總覽頁，**Then** 顯示核准狀態統計、日／週估算用量彙總、接近上限提示與必要防護服務目前是否可用，且不顯示供應商實際帳單金額。
4. **Given** 管理者開啟使用者清單，**When** 選取單一使用者查看詳情，**Then** 顯示最少必要識別資訊、核准等級、日／週已使用、預留中、剩餘估算額度、重置時間與六端點用量摘要；不顯示完整對話、音檔、影像、token 或密鑰。
5. **Given** 有新使用者申請付費資格或有使用者週額度用盡後申請追加，**When** 管理者開啟待審核事項頁，**Then** 顯示對應待審核項目與判斷所需之最少必要資訊。
6. **Given** 管理者對某使用者執行核准、拒絕、切換等級或撤銷，**When** 操作送出並經確認，**Then** 後端逐請求驗證管理者權限後原子套用，下一次該使用者的付費請求或額度查詢即反映新狀態，並留下稽核紀錄。
7. **Given** 管理者對某使用者執行週額度追加，**When** 操作送出，**Then** 必須指定正值金額、適用範圍與不跨週的有效期限；金額與次數由管理者逐次決定且無固定上限，操作原子執行並留下稽核紀錄。
8. **Given** 兩位管理者幾乎同時對同一使用者的同一待審核追加申請送出核准，**When** 後端處理兩個請求，**Then** 僅套用一次追加，不得造成重複追加或不一致的最終額度狀態。
9. **Given** 管理者本身也發出付費 API 請求，**When** 後端執行額度檢查，**Then** 管理者身分不得使其繞過日／週額度與原子預留機制；唯一允許的例外路徑是受冪等、原子更新與稽核約束的追加額度操作。
10. **Given** 請求本文、Header 或前端狀態宣稱使用者具管理者角色，**When** 後端驗證權限，**Then** 僅信任可信來源指定的管理者身分，忽略前端自報的 role 或等效欄位。

## Requirements

### A. 邊界與授權

- **FR-001**: 六個既有付費 API 必須全部納入每次請求的後端資格、額度與輸入檢查，並在上游呼叫前完成。
- **FR-002**: 非 `POST` 的六端點請求必須明確拒絕（例如 405），不得繞過保護檢查。
- **FR-003**: Public、未登入、已登入但未核准、資格撤銷、資格到期與週額度未獲追加核准者，均不得觸發六個端點的上游付費呼叫。
- **FR-004**: Public 功能必須明確限於不呼叫六個付費 API 的功能；公開靜態資產、以及 Geoapify 圖磚由前端直連過渡至後端圖磚代理的架構現況與批准中計畫，須如實記錄。
- **FR-005**: 登入、Session 有效與付費 API 核准資格為不同概念；註冊或登入不得自動授權。
- **FR-006**: 每次受保護請求必須以可信後端資料即時檢查有效資格、等級、撤銷、到期與額度；撤銷後下一次請求即拒絕。
- **FR-007**: 核准、撤銷、等級變更、週額度追加、追加到期與追加拒絕，必須由可信且可稽核的管理流程處理。**本次修訂撤回先前「初版不要求會員管理後台」的排除條款**：本功能第一版必須提供獨立管理者儀表板（見 D 節 FR-031～FR-042）處理上述操作；範圍限定為付費 API 使用資格、等級、額度追加與必要稽核，不擴充為完整會員管理系統。
- **FR-008**: 前端、請求本文、Header、localStorage、使用者自稱的身分／等級／額度不得決定或提高付費權限。

### B. 等級、額度與並發

- **FR-009**: 第一級的估算用量上限為 US$3／日與 US$15／週；第二級為 US$10／日與 US$50／週。
- **FR-010**: 額度以可信後端估算、原子預留與結算控制；不得保證與供應商帳單精確相等，且不得只由前端計算。
- **FR-011**: 日額度與週額度必須分別檢查；日額度獨立有效，不因任何週額度追加而失效，除非未來另行批准。
- **FR-012**: 達週額度後只能由管理者明確追加核准才可繼續呼叫付費 API；追加金額與次數由管理者對指定使用者、指定週逐次決定，不預設固定次數上限，亦不預設累計金額之倍數上限；追加仍以該次核准所屬之週為期限，不得實作為永久無上限豁免（見 D 節 FR-038）。
- **FR-013**: 系統必須使用跨執行個體可靠且 race-safe 的共享控制，避免併發請求使任何已批准上限超額。
- **FR-014**: 額度由每位獲核准使用者各自計算；等級決定該使用者的日／週上限，同級使用者不共用額度。
- **FR-015**: 每次六個付費 API 呼叫前，後端必須以該端點可信的最大估算成本原子預留額度，並在同一決策中檢查日上限與週上限；任一不足時必須在呼叫付費上游前拒絕。
  - **P-G2 收斂**：同一次原子 reserve 必須使用當下有效的 G-B 門檻、目前資格／等級、當週有效追加與日／週餘額。首次 grant 除 `R_e ≤ remaining_day/week` 外，還要求兩窗口在預留前皆 `remaining ≥ G`；即使可變成本請求滿足 `R_e ≤ remaining < G`，也必須回 429 `quotaScope: 'all'`，不新增預留、不授予執行權。通過後僅預留 `R_e`，不是 `max(R_e,G)`，亦不要求預留後仍保有 G。G-B、兩級上限及無固定次數／累計倍數上限的當週追加政策不變。
- **FR-016**: 不得先呼叫供應商再更新用量；重複提交、重新整理、多分頁並發與直接呼叫 API 皆不得突破已定義的估算額度。
- **FR-017**: 若端點無法在呼叫前界定可信最大成本，必須先限制輸入、輸出、時長或其他計費參數；仍無法界定時，不得以本額度政策放行該端點。後端須對六端點分別強制已核准的輸入、輸出、時長與影像上限（數值時點版本見 plan.md §4.2，核准前為提案），超限者在付費上游前拒絕，且不得以平均價格或「通常用量」取代上界。使用者可見的新限制（如單次錄音時長、照片送出前縮圖）屬語音／照片行為變更，須經營運者核准後才可實作。**決策同步（2026-10-06，規劃層級）**：OpenAI 自動重試停用（A＝1，A2）、`speech` 真實呼叫維持受阻且不得以逾時／串流中止／經驗速率當成計費上界（A9）、`transcribe` 採固定格式 PCM WAV＋後端驗證與重建（A10）已規劃核准；上限數值（A1、A3–A5）仍待核准，`speech`／`transcribe` 在證明完成前不得真實呼叫（plan.md §4.2.4、§4.2.6）。
- **FR-018**: 呼叫完成後，後端必須依可取得的供應商用量或既定估算規則結算；成功、明確未計費失敗、逾時與不確定是否計費必須各有一致規則。
- **FR-019**: 內部估算與供應商實際帳單必須分開呈現；不得宣稱估算成本等同實際帳單，並須要求供應商帳戶層級的預算告警或用量限制作為獨立防線。
- **FR-020**: 使用者可在付費功能入口查看自身核准等級，以及日／週已使用、預留中、剩餘估算額度與重置時間；完成一次請求後必須以後端最新狀態更新顯示。
- **FR-021**: 額度查詢失敗、資料過期或必要計數服務故障時，不得顯示虛假的剩餘金額；必要計數服務故障時付費 API 必須 fail-closed。
- **FR-022**: 金額顯示必須定義固定精度與清楚單位；額度權威時區為 `Asia/Taipei`，日窗口於每日 00:00、週窗口於每週一 00:00 由後端重置並提供下一次重置時間。後端決定窗口，前端裝置時鐘不具權威；跨日、跨週與夏令時間／時區偏移不得改變此規則。
- **FR-023**: 額度狀態不得公開邀請名單、其他使用者額度或同級總額度中可識別個人的資訊；若額度歸屬未決，任何「自身剩餘額度」呈現都必須標示為條件式草案，不得標成已核准政策。

### C. HTTP、UX、隱私與相容性

- **FR-024**: `401` 僅用於未登入或 Session 無效；已登入但沒有有效核准資格使用 `403`；日額度或週額度耗盡使用 `429`；必要防護服務故障使用 `503`。
  - **2026-10-06 隔離 pipeline 文件澄清（使用者已批准，非實作授權）**：method／解析前大小檢查後，先做登入驗證前的匿名 admission 入口防濫用限流；被限流者優先回 `429 RATE_LIMITED`，入口限流故障回統一 503。其餘請求仍須通過 Session（401）、有效核准資格（403）及已登入者限流，才可進入成本／額度流程。匿名 admission 不授權匿名付費使用、不建立匿名付費額度；不得信任客戶端 IP／代理 Header，也不得讀取或洩漏既有預留。正式限流數值與真實 adapter 未核准；本澄清不更改管理／圖磚端點契約。
- **FR-025**: 日額度與週額度 429 必須分別說明狀態與恢復條件，不得合併為通用文案。「額度已滿」只適用實際 `exhausted`；`below_floor` 尚未耗盡，必須明示剩餘不足預留門檻；`request_insufficient` 只影響本次操作，不得稱額度已滿或使地圖／其他較低成本功能全域不可用。保留既有 code 與 `quotaScope`；成本模型無效仍為統一 503，不使用額度文案。**A6 六列文案已批准**見下節；其他功能仍獨立檢查資格、額度及防護狀態，不承諾必然可用。判定邏輯仍依 plan.md §4.5.3，未變更 G-B。
- **FR-026**: 403 必須清楚表達「資格未核准、已撤銷或已到期」而不揭露敏感內部資料；503 必須清楚表達「防護服務暫時無法確認使用狀態」。
- **FR-027**: UI 不得自動重試任何被拒絕或失敗的付費請求；登入、核准、額度恢復或服務恢復後，都須由使用者重新明確操作。
- **FR-028**: PWA 不得快取憑證或任何 `/api/` 私人回應；舊快取不得繞過新政策。已公開或已快取靜態內容不宣稱可遠端收回。
- **FR-029**: 日誌僅記錄稽核所需最小資料，且不得記錄 token、secret、完整對話、音檔、影像或完整核准名單。
- **FR-030**: 正式站模式切換、外部服務啟用與部署必須分別取得明確批准；本規格不核准其中任一項。
- **FR-049**: 成本模型無效、過期、未證明或遭封鎖時，付費端點必須在呼叫上游前回 `503 PROTECTION_SERVICE_UNAVAILABLE`，並使用「保護服務暫時無法確認使用狀態，付費功能先暫停。請稍後再試。」；內部原因不得透過回應、header 或可觀察差異洩露價表版本、模型、封鎖狀態或設定。`COST_MODEL_INVALID`、`COST_MODEL_UNSUPPORTED`、`COST_BOUND_UNPROVEN`、`COST_MODEL_BLOCKED` 等只供內部稽核。
- **FR-050**: 同鍵同指紋重複請求回 `409 DUPLICATE_REQUEST`，繁體中文訊息為「此操作已送出，請查看目前狀態。」；同鍵不同指紋回 `409 IDEMPOTENCY_CONFLICT`，訊息為「操作識別碼與原請求不一致，請重新確認操作。」。兩者均不得自動重送、不得重新授予上游執行權。「查看目前狀態」不得暗示成功；查詢方式、回應欄位與授權細節須由後續契約另定。
- **FR-051**: 預留金額只能由可信後端估算器依經核准 registry 計算。後端必須驗證價表版本、有效期間、live／封鎖狀態與端點適用性；呼叫端不得指定金額、價表版本或以更換版本字串解除封鎖。只有新版本重新滿足上界證據與核准條件後才可啟用；目前 production 六端點均維持 `live: false`。
  - **P-G1 收斂**：`E_live` 只納入當下可信、有效、數值已批准、上界及 A＝1 證據成立、已實際啟用且版本／成本摘要未封鎖的端點；G 仍為其中最小 `R_max,e`，無固定常數。單請求固定一份後端 registry 快照以估算、產生 HMAC 與綁定預留；快照不具有永久授權效力。registry 發布、停用與雙封鎖須與 reserve 在同一共享原子邊界線性化；reserve 前生效的變更使舊快照拒絕為統一 503，不能自動換版重試。reserve 先取得的有效首次 grant 不被後續 registry 更新追溯作廢，仍按原成本／窗口與 lease 單次執行及保守結算；後續新 reserve 必須使用最新狀態。此語意沿用既有追加／撤銷的非追溯政策，不承諾追回已發生的呼叫。
  - **2026-10-06 Batch-M3a 核准補充（僅隔離修補）**：registry 由伺服器依賴注入，選定模型、標準計費 tier、attempts＝1、價表與上限；預留金額由後端估算器計算。成本參數摘要由後端穩定編碼計算，涵蓋模型／白名單、tier、attempts、單價、上界、安全係數與允許的 detail；不得由呼叫端指定。store 在原子預留內同時判斷版本封鎖與摘要封鎖，同版本同端點不得對應不同摘要；相同成本參數僅更換版本仍不得放行。新參數與新版本仍須符合核准及上界證據條件；到期或封鎖不妨礙既有預留保守結算。此批准不包括 pipeline、handler、狀態查詢或正式啟用，也不證明真實輸入／成本上界。
- **FR-052**: 預留 lease 必須逐端點依已核准的最長執行時間加結算緩衝決定，不得將固定秒數套用至所有端點。本規格不核定任何具體秒數。到期清理／對帳須可重複執行且具冪等性；到期預留轉為 `uncertain`，保留在原日／週窗口、不退款、不重放。shared store timeout 表示操作結果未知，不代表操作未完成，不得據此釋放額度、重試寫入或重送上游。排程或觸發方式列為後續實作與驗證，不在本輪建立服務。
  - **2026-10-06 H1-R1 核准補充（僅時鐘倒退隔離修補）**：同次新預留流程的可信時間必須有效且依 `estimationTime ≤ commandTime ≤ grantTime` 不倒退；command 早於 estimation 須在 `store.reserve` 前拒絕。grant 無效、早於 command 或已到達 lease 到期時間均不得取得 `executionGrant`。不得 clamp、忽略倒退或偽造時間；相等可接受但不豁免成本模型效期及 lease 判斷。store 已可能完成預留時，拒絕不得退款或重授權／重放；此新授權檢查不套用至歷史預留保守結算。正式秒數、pipeline、handler／UI、T135 與真實整合均不在本批範圍。
- **FR-053**: `uncertain` 預留繼續占用其建立時的原日／週窗口，不占用新窗口。對帳只可依可信證據及可稽核流程處理，不得自動退款；晚到上游結果只記錄，不得自行改變既有額度。結算超過預留時須如實計入超額、產生可驗證的超額與價表版本封鎖結果；重複結算只有在金額及結算語意與原結果一致時才可視為已套用，否則須回報衝突／無效轉換。日誌及紀錄保存期限尚未批准，不得自行定案。
- **FR-054**: 請求內容指紋必須使用伺服器持有金鑰的 HMAC；`estimateInputs` 僅能包含明列的數值與列舉欄位，不得保存任意字串、完整對話、音訊或圖片。只保留執行授權、額度與稽核所需最少資料，並限制讀取主體與用途；保存期限及金鑰輪替細節列為待決，不建立金鑰或寫入秘密值。
  - **2026-10-06 Batch-M2 核准補充（僅隔離 mock）**：原始請求內容只在記憶體中產生 keyed digest；store 不接受普通 `contentDigest`。使用者內容與後端可信成本參數分離，model、billing tier、attempts 不得由 request body 或任意 `estimateInputs` 宣告；缺少／矛盾的可信參數、HMAC key 或數值上限設定必須 fail closed。逐端點欄位見 data-model §15.1；注入式數值僅為測試 fixture，無 production fallback。此批准不建立 registry、不解決 A4、不核定正式上限；speech 維持受阻。
- **FR-055**: 付費請求必須先驗證目前 Session 與核准資格，再回應冪等鍵重複／衝突；已撤銷或無資格者一律回 `403 ACCESS_NOT_APPROVED`，不得藉重複請求取得原預留識別碼、狀態或其他原請求資訊。
  - **2026-10-06 隔離 pipeline 順序澄清（使用者已批准）**：有界解析、語意／格式與成本相關輸入驗證在預留前完成，避免無效輸入先占額再退款。預留後仍須核對同次原子回傳、可信時間及 lease，只有首次有效 `executionGrant` 才能執行一次 mock upstream，並保留結算／錯誤處理。不得省略 Session／資格、限流、registry 或日週額度檢查；不核准產品上限、handler 接線或程式實作。上方 403 要求適用於通過 method／大小／匿名 admission 的請求；入口拒絕也不能查預留。
- **FR-056**: 價表失效、封鎖、estimate input 不合法、store timeout、超額結算與重複結算衝突等情況均須 fail-closed，不得造成未授權上游呼叫。正常結算且佐證有效時，內部標示已入帳，原付費 API 依原請求結果處理；超額須如實入帳並原子封鎖版本與成本參數摘要，內部明確標示「已入帳，但成本上界遭突破」，原付費 API 對外仍回 `503 PROTECTION_SERVICE_UNAVAILABLE`，不得包裝為一般成功。佐證或 usage 矛盾亦對外 503，不得推論 store 尚未入帳、退款或重送上游。內部結算必須使用獨立狀態而非通用 `ok:true`；錯誤外顯依 FR-049／FR-050 與錯誤契約。

### 額度顯示與時間窗口可觀察要求

- 金額以美元 `US$` 顯示，至少保留到美分（小數點後兩位）；若內部估算需要更高精度，後端可保留更細單位，但 UI 不得用多餘小數營造實際帳單精確性。
- 付費功能入口顯示「已使用」「預留中」「剩餘估算額度」三者時，必須清楚標示為內部估算額度；不得稱為供應商帳單。
- 日／週重置時間必須由可信後端回傳，並附可理解的本地化顯示；權威時區為 `Asia/Taipei`，日窗口於每日 00:00、週窗口於每週一 00:00 重置，前端裝置時鐘不具權威。
- 額度查詢失敗、資料過期或分頁閒置過久時，顯示「目前無法確認額度狀態」等狀態，不顯示舊的剩餘金額作為可用保證。
- 舊分頁、離線 App Shell、前端快取或 localStorage 不得作為授權依據；所有付費 API 呼叫仍以後端即時預留結果為準。

#### A6 四種額度語意與精確文案（本輪已批准）

四種語意為日耗盡、週耗盡、`below_floor`、本次 request 不足；後兩者各有日／週版本，故共有六列。以下均為 HTTP 429。`exhausted` 以 `limit − used ≤ 0` 判定；`below_floor` 以未耗盡且 `remaining < G` 判定；request 不足以日／週皆非全域不可用且 `R_e > remaining` 判定。G 仍依目前可用端點的 **最大合法輸入預留**計算，不改成最小輸入成本；「不足門檻」不宣稱任何極短輸入在數學上都不可能預留。

| --- | --- | --- | --- | --- | --- |
| 日耗盡／day | `DAILY_QUOTA_EXHAUSTED` | `all` | 當日額度已滿 | 當日額度已滿，請在下一個日額度週期後再試。你仍可查看公開內容。 | 請在下一個日額度週期後確認最新額度，再手動重試。 |

### D. 獨立管理者儀表板與權限

- **FR-031**: 管理者儀表板必須提供獨立於一般使用者介面的頁面與資料 API，範圍限定為付費 API 使用資格管理：核准狀態總覽、使用者清單與詳情、待審核事項、操作與稽核；不得擴充為完整會員資料管理、行銷、通知或其他非本功能範圍之後台能力。
- **FR-032**: 管理者頁面與資料 API 之每一個讀取與異動端點，必須逐請求以可信後端驗證管理者權限；未登入或 Session 無效者回應 401，已登入但非管理者者回應 403，兩者均不得回傳管理資料，且不得因擁有付費核准等級而取得管理權限。
- **FR-033**: 管理者身分之指定與撤銷必須來自可信、不可由使用者自行提升權限之來源；後端不得信任前端請求中的 role、isAdmin 或等效自報欄位作為授權依據。具體來源機制待後續 Plan 決定。
- **FR-034**: 管理者總覽頁必須顯示核准狀態統計（例如待審核、已核准、已撤銷、已拒絕人數）、日／週估算用量彙總、接近日／週上限之使用者提示，以及必要防護服務（授權、額度、原子預留）目前是否可用之狀態；不得顯示供應商實際帳單金額。
- **FR-035**: 使用者清單與詳情頁必須顯示每位使用者之最少必要識別資訊、目前核准等級、日／週已使用、預留中、剩餘估算額度、下一次重置時間，以及六個受保護端點各自之用量摘要；不得顯示完整對話內容、音檔、影像、token 或密鑰。
- **FR-036**: 待審核事項頁必須列出新使用者付費資格申請與週額度用盡後的追加額度申請兩類項目，並提供管理者判斷所需之最少必要資訊。
- **FR-037**: 管理者對核准、拒絕、切換等級、撤銷與追加額度之異動操作必須為原子操作；當多位管理者同時對同一使用者或同一待審核項目送出核准或追加時，不得造成重複追加或不一致之最終狀態。
- **FR-038**: 追加額度操作由管理者對指定使用者、指定週逐次決定追加金額（正值）與追加次數；不預設固定次數上限，亦不預設累計金額之倍數上限。每次追加仍必須明確指定金額、適用範圍與有效期限，且只對指定使用者及該週有效，到期不得跨週或永久豁免；日上限仍獨立有效。操作須使用冪等鍵防止重複提交、以原子操作更新該週額度，並記錄核准之管理者身分、時間、對象、金額與原因。因無累計上限，個人週額度機制不得被視為整站估算成本或供應商實際帳單之上限保證，須配合供應商帳戶用量監控與管理者操作提醒（見 Plan §5.3）。
- **FR-039**: 管理端點之異動操作必須具備防止 CSRF 與重複提交（例如以冪等性或一次性請求識別）之保護；重要異動（撤銷、降級、追加）之使用者介面必須要求管理者明確確認，但此確認步驟不得取代後端逐請求授權檢查。
  - **2026-10-08 本機確認恢復補足**：落實既有防重複提交與未知同鍵原則；未知結果在目前確認區保留原操作鍵，不可取消換鍵，只能明確手動確認。後續確認被拒絕不推論先前未知異動未成立；首次明確拒絕可取消修正。鍵盤開啟聚焦確認區，送出前取消回原按鈕，成功刷新後聚焦詳情確認按鈕；錯誤 alert、處理中 status。離頁取消 client 等待不代表 server rollback，不新增持久儲存或後端權限。
- **FR-040**: 管理者亦受本功能之付費 API 成本控制約束；管理者操作不得使管理者自身或其他使用者無限制繞過日／週額度或原子預留機制。追加額度為唯一允許之例外路徑，其金額與次數由管理者依 FR-038 逐次決定且無固定上限，但仍受冪等、原子更新與可追溯紀錄約束。
- **FR-041**: 管理稽核紀錄必須記錄每次核准、拒絕、切換等級、撤銷與追加操作之管理者身分、對象使用者、操作類型、時間，以及追加操作之金額／範圍／期限等最少必要欄位；不得記錄或顯示完整對話、音檔、影像、token、密鑰或完整邀請名單匯出。
- **FR-042**: 管理資料與操作之顯示範圍僅限管理者儀表板本身；一般使用者付費功能入口與 Public 頁面不得呈現管理資料或管理操作入口。

### E. Geoapify 方案 A 與靜態地圖替代

- **FR-043**: Public、未登入、已登入但未核准、資格撤銷、資格到期，以及日或週額度使付費功能暫不可用時，探索附近的地圖位置必須顯示不含真實地理資料的靜態東京風格示意圖；不得初始化 Leaflet、Geoapify 或任何會載入圖磚的互動地圖元件。僅以 CSS 隱藏已初始化的地圖不符合本要求。
- **FR-044**: FR-043 的受限狀態下，頁面載入、重新整理、舊分頁恢復、模式切換、資格或額度變更、背景預取及自動重試均不得發出圖磚請求或 `/api/places` 呼叫；被拒絕的舊搜尋不得在登入、核准、窗口重置或服務恢復後自動補送。後端圖磚代理與其快取層均不得在資格或額度狀態變更後，於未重新驗證的情況下對同一使用者提供圖磚回應。**口徑澄清（2026-10-07，措辭同步，待使用者確認）**：本條「不得發出」「為零」指前端依最新狀態不主動發出的請求；狀態變更前已掛載且尚未感知變更的舊分頁，其殘留請求前端不保證為零，但抵達代理後必須逐請求以 401／403／429 拒絕且對 Geoapify 上游呼叫為零（見 FR-043、SC-011 與 plan.md §6.5）。
- **FR-045**: 有效第一級、第二級或管理者使用者僅在本身資格有效且日／週額度可用時，得按既有功能使用互動地圖；`/api/places` 只可由使用者明確搜尋觸發，且每次仍須通過後端授權、最大成本原子預留與日／週額度控制。互動地圖資格不得被解讀為 `/api/places` 已預先獲准。
- **FR-046**: 靜態示意圖必須以繁體中文可見文字標示「示意圖」，提供說明其非即時地圖與非真實地理資料的替代文字，且不得呈現即時位置、可點選地點、marker、pan／zoom 或導航能力；須提供前往既有公開內容的操作，圖片載入失敗時仍須顯示可讀文字狀態。
- **FR-047**: 靜態示意圖正式資產的取得、授權、最佳化與整合方式屬後續實作事項；聊天附圖只作視覺參考，不得假定 repository 已存在圖片檔或把它當作真實地理資料。
- **FR-048**: 合資格使用者的所有圖磚請求必須經由後端圖磚代理逐請求驗證 Session、核准資格、六端點日／週 US$ 額度可用性與獨立圖磚額度後才轉發至上游供應商；日或週 US$ 額度不可用時須在查詢代理快取前回對應 429。前端不得保留任何可繞過代理的直連上游路徑，也不得允許使用者或請求本文指定任意上游 URL、host 或樣式參數。代理與其快取層必須確保撤銷或額度耗盡後，下一筆抵達代理且完成驗證的圖磚請求必然被拒絕；此要求不涵蓋撤銷生效前已完成之請求，或已呈現於使用者裝置上之圖磚影像位元組，此二者之不可回溯性須於驗收語意中如實記錄，不得宣稱可追溯撤回。

## Success Criteria

- **SC-001**: 隔離環境中，Public、未核准登入者及週額度未獲有效追加核准者對六端點的直接呼叫 100% 在上游前被拒絕。
- **SC-002**: 第一級與第二級測試帳號在各自日／週額度內可成功使用六端點；超額請求不觸發上游。
- **SC-003**: 每一個日額度、週額度、資格未核准與防護服務故障情境，都回傳正確的 429／403／503 與不同繁體中文恢復訊息。
- **SC-004**: 撤銷、等級變更、追加核准到期或拒絕後，下一次請求反映最新資料；並發測試不超過核准額度。
- **SC-005**: 公開靜態資產維持可用；Geoapify 依方案 A 僅限有效核准且日／週額度可用者載入；PWA 不快取 `/api/` 回應或憑證。
- **SC-006**: 多個同時請求、重複提交、重新整理頁面與直接 API 呼叫的測試，均證明無法藉競態超過日／週估算額度；上游 mock 呼叫數不得超過成功預留數。
  - **本輪新增驗收義務（待測）**：在同一成本快照，以可變成本合法 fixture 驗證 `R_e ≤ remaining < G` 的日、週與雙窗口拒絕；G−1／G、R_e−1／R_e、`R_e < G` 成功只扣 R_e；以受控 barrier 驗證 registry 更新／停用／非目標端點封鎖改變 G、目標端點封鎖、追加／撤回與 reserve 的兩種線性化順序。拒絕上游呼叫零次；首次 grant 最多一次；正式跨 writer Redis/Lua 證據另驗，不以 memory mock 代替。
- **SC-007**: 成功、明確未計費失敗、逾時與不確定是否計費四類結算情境皆能產生一致的已使用、預留中與剩餘額度顯示，且不宣稱為供應商實際帳單。
- **SC-008**: 額度查詢故障、資料過期、日／週跨期與資格撤銷情境下，UI 不顯示虛假剩餘金額，付費 API 維持後端 fail-closed，公開功能仍可用。
- **SC-009**: 隔離環境中，未登入或 Session 無效者對所有管理資料端點與管理異動端點 100% 回應 401，已登入的一般登入者、第一級與第二級核准使用者 100% 回應 403；兩種拒絕均無管理資料外洩，僅可信來源指定之管理者身分可成功讀取與異動。
- **SC-010**: 並發測試中，兩位管理者對同一待審核項目或相同 `idempotencyKey` 送出的同一邏輯操作最終只套用一次；對同一使用者以不同 `idempotencyKey` 建立的獨立追加則各自原子累加且不得遺失更新。稽核紀錄可追溯每次操作之管理者身分、對象、類型與時間；管理者自身之付費 API 呼叫仍受日／週額度與原子預留機制約束。
- **SC-011**: 隔離瀏覽器環境中，Public、未登入、已登入但未核准／已撤銷／已到期，以及日或週額度暫不可用的每一情境，在初次進入、重新整理、舊分頁恢復、模式或資格變更後，圖磚請求數與 `/api/places` 呼叫數皆為零；驗證方式包含以 Network／HAR 觀察瀏覽器實際請求，以及直接對後端圖磚代理端點發出請求以確認拒絕且無對應上游呼叫（可由後端 log／mock 驗證）。撤銷情境須額外確認「下一筆抵達代理的請求」被拒絕，同時明確排除「撤銷前已完成的請求」與「裝置上已呈現圖磚影像」兩類不宣稱可追回之殘留；此項目前為待測，不得以 CSS 隱藏、元件不可見或單元 mock 取代網路證據。
- **SC-012**: 有效核准且日／週額度可用的第一級與第二級測試帳號，其既有互動地圖、明確搜尋、結果選取與導航交接無回歸；Places 搜尋仍受後端授權與額度控制。此項目前為待測。
- **SC-013**: 以隔離測試逐一驗證成本模型無效／過期／未證明／封鎖皆只對外回 `503 PROTECTION_SERVICE_UNAVAILABLE` 與指定繁體中文文案，回應不含內部原因或價表資訊且上游呼叫數為零；有效資格檢查先於冪等查詢，已撤銷者即使重複提交仍回 403。
- **SC-014**: 對兩種 409 驗證指定 code 與逐字文案；同鍵重複／衝突均無第二次執行權、無自動重送，狀態提示不聲稱成功；狀態查詢介面在契約定義前不得被假定存在。
- **SC-015**: 以各端點執行上限與結算緩衝驗證 lease 設定不共用固定秒數；到期清理可重複執行而不改變已完成結果，逾期項目轉 `uncertain` 並保留在原日／週窗口。注入 store timeout 後不得釋額或重送上游；真實 store key/hash-slot、原子更新與保存策略須有實際 Redis/Lua 證據，mock 不算通過。
- **SC-016**: 重複結算同金額同語意才回已套用；同 reservation 的不同金額或結算語意必須拒絕且不變更額度。超額結算可查驗實際入帳金額、超額數與版本／摘要雙封鎖；內部明確為已入帳但成本上界遭突破，原付費 API 仍回 503，不包裝一般成功。正常結算使用獨立內部狀態；usage／佐證矛盾亦 503，不推論尚未入帳、不退款、不重送。晚到結果只留下稽核紀錄且不退款。此批只驗證隔離契約，handler 外顯仍待整合。
- **SC-017**: 驗證 HMAC 指紋不含可還原請求內容；`estimateInputs` 的每個端點只接受列明數值／列舉鍵，任意鍵或字串、對話、音訊與圖片均拒絕或不持久化；存取權限與最小化規則可由測試／稽核證據查驗。保存期限與金鑰輪替尚未決，不得以測試通過宣稱已定案。
